# v0.5.88 — TLS reload rollback on invalid certificate

## Scope

v0.5.88 adds a defensive test for the failure path of
`cmq_tls_reload`. The reload implementation builds a new
`SSL_CTX` off-line and swaps it only after certificate and key
validation succeeds. That atomic rollback contract was not
covered by a real listener test.

## What v0.5.88 ships

- **`tests/test_tls_e2e_handshake.c::tls_reload_invalid_cert_preserves_context`**:
  - Start a TLS server on port 25584 with a valid certificate.
  - Replace the configured certificate file with malformed PEM.
  - Assert `cmq_tls_reload` returns `-1`.
  - Restore the valid certificate file.
  - Start the listener and complete a real TLS handshake.
  - Assert the old context still serves traffic.

No production change is required. The test locks in the
existing atomic-swap invariant: a failed reload must not
destroy or replace the last known-good context.

## Why this matters

Certificate rotation is operationally routine, and failed
reloads are expected during interrupted deployments or bad
configuration updates. The safe behavior is to reject the
new material while continuing to serve with the previous
valid context. Replacing the old context before validation
would turn a recoverable configuration error into a TLS
outage.
