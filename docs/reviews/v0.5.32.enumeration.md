# v0.5.32 — Per-listener TLS acceptance path

## Scope
v0.5.31 allocates `tls_config_slots[1..3]` but the accept callback
(`accept_cb` in `cmq_server.c`) still uses slot 0 for all
connections via `client_tls_handshake`. v0.5.32 wires the
per-listener selection so a connection arriving on listen fd
`port+1` uses slot 1's TLS config.

Currently `cmq_server_t` has `listen_fds[0..3]` and
`tls_config_slots[0..3]`. The accept callback knows which fd
fired (its first arg). We map fd → slot index via a small linear
scan (at most 4 entries) and stash the slot on the new
`cmq_client_t`.

## Design (performance-first, safety, reliability)

### Slot lookup helper

```c
/* Returns the slot index that owns this listen fd, or 0 if no
 * per-listener slot was configured (fallback path). */
int srv_find_tls_slot(cmq_server_t *srv, int listen_fd);
```

Linear scan over `listen_fds[0..CMQ_MAX_LISTENERS-1]`. O(4) — ns-scale.

### Client struct change

`cmq_client_t` gets `int tls_slot;` (0 = slot 0 / default; 1-3 =
per-listener). Set in `accept_cb` BEFORE `cmq_client_create`
returns. Read in `client_tls_handshake`.

### Handshake path update

`client_tls_handshake(srv, client)` reads `client->tls_slot` and
indexes into `srv->tls_config_slots[client->tls_slot]`. Falls back
to slot 0 if the slot is NULL (the listener was unencrypted; a
plaintext connection is fine).

### Fallback semantics

- If a listen fd has no matching tls_config_slot (listener enabled
  but no cert configured), `srv_find_tls_slot` returns 0, the client
  uses slot 0's TLS. If slot 0 is also unallocated, the handshake
  is skipped (plaintext).
- This matches the v0.5.31 allocation log: a misconfigured
  listener falls back to slot 0 (or plaintext).

### Safety

- `tls_slot` is set on the new client BEFORE any other thread can
  see it (the client is created in the accept thread and published
  via the worker queue under a lock). No atomic needed.
- A NULL slot check in `client_tls_handshake` is defensive: if the
  slot lookup returns a bad index, the function returns 0 (no
  handshake), and the client is destroyed upstream.

### Reliability

- The accept path is performance-critical. Linear scan of 4 fds is
  ~10 ns; negligible compared to the existing accept work (~us
  scale).
- The 2nd accept thread (`accept_thread_func`) is currently a stub
  in v0.5.17; v0.5.32 leaves it alone (separate scope).

## Risk
- `accept_cb` is hot. A linear scan of 4 fds is fine. If
  `CMQ_MAX_LISTENERS` ever grows beyond ~16, switch to a hash.
- The `client->tls_slot` default value (calloc zero-initializes)
  is 0, which is the right default for the single-listener case.
