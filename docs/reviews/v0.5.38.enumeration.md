# v0.5.38 — handle_publish persistence integration test

## Scope
v0.5.7 / v0.5.19 unit tests cover the F5 WAL file format and the
recovery loop in isolation. v0.5.37 ships an end-to-end subscriber
restart test. v0.5.38 closes the remaining gap: an integration
test that verifies `handle_publish` writes to the WAL when
`srv->filestore` is configured, and the recovery bookkeeping is
accessible after a server restart.

The test does NOT drive a real client PUBLISH through handle_publish
(which would require a full event-loop test driver). It writes
directly to the filestore via `cmq_filestore_append` and verifies
that the recovery code on the next `cmq_server_create` can read it
back without crashing and exposes the `stat_messages_replayed` field.

## Design

### Test flow (`tests/test_persist_replay.c`)

1. `system("rm -rf /tmp/cmq-test-v0538-wal")` + mkdir.
2. `cmq_config_t cfg = { ..., persist_dir = ... }`.
3. Phase 1: `cmq_server_create(&srv_a, &cfg)`. Append a 64-byte
   record via `cmq_filestore_append`. Sync. Assert `last_seq == 1`.
   `cmq_server_destroy(srv_a)`.
4. Phase 2: `cmq_server_create(&srv_b, &cfg)`. Verify the server
   is healthy and `stat_messages_replayed` is accessible (the
   value is not asserted because the replay dispatcher runs on
   a worker thread that may not have completed by the time the
   test checks — see below).
5. `cmq_server_destroy(srv_b)`. `system("rm -rf ...")` cleanup.

### Honest caveat

The replay dispatcher uses parallel workers (v0.5.7 chunked
replay) that may not finish before `cmq_server_create` returns
to the caller. So we don't assert `stat_messages_replayed > 0`.
The test verifies that the field is **accessible** and that the
second `cmq_server_create` doesn't crash on the replayed record.
If the dispatcher finished, the stat will reflect the replayed
count; if it didn't, we still get a clean server.

A follow-up test (v0.6 scope) could run `cmq_server_run` on a
thread, sleep until the replay completes, and assert the stat.
That's a real end-to-end test; v0.5.38 is a smoke test.

## Risk
- Port collision: the test uses port=0 (no bind), so no actual
  listening. The cmq_server_run path is never entered.
- `cmq_filestore_append` writes raw bytes; the format depends on
  the wire format produced by `handle_publish`. The test uses a
  fake payload (4 bytes of 1, 2, 3, 4) that doesn't conform to
  the cmq wire format — but since we're only verifying the file
  round-trip on the producer side (last_seq == 1), the replay
  doesn't need to parse the payload. The replay would fail to
  parse this fake payload and silently drop it on the subscriber
  side; that's fine for the smoke test.

## Out of scope for v0.5.38
- The MQTT bridge adapter (v0.5.36) doesn't persist to WAL. The
  bridge persists via `cmq_server_publish`, not `handle_publish`,
  so the existing persist hook doesn't fire. Adding bridge WAL
  persistence is a separate scope (v0.5.39+ or v0.6).
- Real end-to-end test driving a full PUBLISH through handle_publish
  with a live client connection. The existing event-loop-driven
  tests (`test_request_reply.c`, `test_publish.c`) cover the
  normal client flow but not specifically the WAL-write path.
