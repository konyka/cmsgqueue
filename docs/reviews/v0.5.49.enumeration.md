# v0.5.49 — Publish-side subject rewrite

## Scope
D7 from v0.5.41: export/import gate cross-account delivery, but a
publish still matches the **wire** subject. NATS account mappings
(`foo.*` → `bar.*`) do not exist.

P3 leftovers (OTel, HTTP/2, JWT, JetStream, EOS, Kafka compact)
stay deferred. F14 `cmq_quota_check_connect` stays unwired.

## Design (performance-first, safety, reliability)

### Maps on the perms row

Up to 16 `{src, dest}` rows per account, beside export/import.
`src` is a token pattern (`*`, `>`). `dest` is a template:
literals, `*` (next capture), `$1`..`$9`, and a final `>`.

First match wins. Same `src` upserts. Soft-delete of the account
drops its maps.

### Hot path

`map_total` on the manager. `0` → rewrite is skipped (one
atomic load). No extra lock on the common no-map path.

### Where it runs

Export ACL and F16 still see the **original** subject (what the
client published). Rewrite happens after those gates, before
sublist match. The WAL keeps the original frame; replay applies
the live map table.

REQUEST subjects rewrite. `_INBOX.` / RESPONSE do not.

### Safety

- Dest templates are validated at add (no mid-token wildcards,
  `$N` cannot exceed src `*` count, `>` only if src has `>`).
- Rewrite overflow or an invalid result rejects the publish.
- Maps are admin API only (same trust as export/import).
