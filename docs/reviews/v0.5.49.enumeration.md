# v0.5.49 — TLS 1.3 mTLS second attempt: race persists

## Scope

v0.5.48 attempted to lift the v0.5.46 TLS 1.2 cap by wiring
the post-handshake auth path. The first attempt tore down
authenticated clients prematurely. v0.5.49 tried again with
a tighter design — adding a `handshake_flushed` guard to ensure
`cmq_tls_flush` fires exactly once per session, plus tightening
the CRL check from `CRL_CHECK_ALL` (entire chain) to
`CRL_CHECK` (leaf only).

## What was tried

1. **`handshake_flushed` guard** on `cmq_tls_session_t`. The
   `cmq_tls_flush` implementation now checks this flag and
   skips the `SSL_write(NULL, 0)` call if already flushed.
   Hypothesis: the v0.5.48 race was caused by `SSL_write`
   firing multiple times on a session mid post-handshake
   processing, corrupting its state.

2. **`cmq_tls_handshake_failed` accessor**: same as v0.5.48,
   but used to gate teardown decisions.

3. **`info_cb`** watching for `SSL3_AD_HANDSHAKE_FAILURE`
   (40), `SSL3_AD_BAD_CERTIFICATE` (42), and
   `SSL3_AD_CERTIFICATE_REVOKED` (44).

4. **`CRL_CHECK` instead of `CRL_CHECK_ALL`**: with
   `CRL_CHECK_ALL`, OpenSSL requires the entire chain
   (including the leaf) to carry a CRL distribution point;
   certs without CDP fail closed with
   `X509_V_ERR_DIFFERENT_CRL_SCOPE` (44). The OpenSSL
   issue #23325 documents this scope-matching bug. With
   `CRL_CHECK` only, the leaf is checked against the CRL;
   if the leaf has no CDP, no CRL check fires (the leaf
   is accepted).

## Result

Same race condition as v0.5.48: authenticated mTLS clients
(sub-test A of `mtls_required`) are torn down with
"unexpected EOF" — the client doesn't see a clear alert,
just connection closure. The flush guard didn't help.

## Root cause analysis

The unexpected EOF (no alert) suggests the server is closing
the connection BEFORE the post-handshake exchange completes.
Possible causes:

1. **OpenSSL internal state corruption**: `SSL_write(NULL, 0)`
   after the initial handshake_done fires OpenSSL's post-handshake
   CertificateRequest logic. If the SSL state is already mid
   flight (e.g., the client's cert response is in flight when
   we call `SSL_write`), OpenSSL might enter an invalid state
   and silently close.

2. **Race with the read-path resume**: the v0.5.45
   `client_read_cb` fires `cmq_tls_handshake` on every EV_READ
   until `handshake_done`. After `handshake_done=1` and the
   flush, the next EV_READ processes the client's cert response.
   If both fire close in time, the SSL state may be advanced
   past the cert response without proper processing.

3. **The `SSL_VERIFY_FAIL_IF_NO_PEER_CERT` flag may not be
   correctly set per-SSL**: when we call `SSL_set_verify`
   inside the client_hello_cb, the flag is set on the SSL
   but may not be honored for the post-handshake flight
   because OpenSSL 3.5's state machine treats post-handshake
   cert exchange differently from the initial handshake.

Without instrumenting OpenSSL internals (impractical) or
reading OpenSSL source, we cannot precisely identify which
of these (or another cause) is responsible.

## Resolution

Same as v0.5.48: **revert all production code**. The v0.5.46
TLS 1.2 cap stays. TLS 1.2 mTLS is the only stable path.

## What v0.5.49 actually ships

Nothing — production code is unchanged from v0.5.47.

## Deferred to v0.5.50+

- Investigate OpenSSL 3.5 source for the post-handshake state
  machine to understand the exact race.
- Consider switching to a custom verify callback that decides
  post-handshake outcome before reaching the SSL state machine.
- Alternative: implement mTLS verification at the application
  layer (not relying on OpenSSL's TLS 1.3 post-handshake) by
  reading the client cert off the wire separately.
- Or: accept TLS 1.2 as the only mTLS path and document the
  limitation in the public API.
