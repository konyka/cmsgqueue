# v0.5.89 — ALPN 3+ protocol list server preference

## Scope

v0.5.89 adds a defensive test that locks in the ALPN
server-preference contract for protocol lists with more
than two entries. The existing ALPN tests (v0.5.82,
v0.5.83, v0.5.85) all use 2-element protocol lists. A
regression in `cmq_tls_alpn_select_cb`'s iteration logic
that broke at length 3 would slip through those tests
uncovered.

The callback walks the server's wire-format list and
returns the first server-listed protocol that the client
also offers. For 3-element lists, the iteration must
correctly handle:
- Three server protocols, all in the client's list.
- Three server protocols, only the third is in the
  client's list (server's first preference is NOT in
  client's list).
- A protocol list where the byte-length arithmetic has
  the same shape as 2-element lists but with a third
  cycle.

## What v0.5.89 ships

### Defensive test

(`tests/test_tls_e2e_handshake.c`):

- **`tls_e2e_handshake, alpn_three_protocols_server_preference`**:
  - Server: ALPN "h2,http/1.1,nats" on port 25585.
  - Client: ALPN "nats,h2,http/1.1" (different order;
    no overlap of the server's first preference "h2"
    appearing first in the client list — actually it does
    appear, but as the client's second choice, and
    server-preference wins regardless).
  - Asserts the negotiated protocol is "h2" (the
    server's first preference), NOT "nats" (the client's
    first preference) and NOT "http/1.1" (the server's
    second preference).
  - Use 3-element lists on both sides so the callback's
    iteration logic is exercised beyond 2-element lists.

Catches regressions: a future change to
`cmq_tls_alpn_select_cb` that walks the client's list
first (instead of the server's), or that miscounts
length fields, would break the contract on 3+ element
lists.

## Why this matters

RFC 7301 server-preference with multi-element lists is
the foundation of HTTP/2 + HTTP/1.1 + WebSocket co-existence
on a single TLS endpoint. A regression at length 3 would
silently downgrade ALPN negotiation in any deployment
that lists 3+ protocols (a common pattern for "h2 preferred,
fall back to http/1.1, then optional experimental").

## Deferred (unchanged)

- TLS 1.3 mTLS via post-handshake auth. The TLS 1.2 cap
  remains in place for the initial `tls_build_ssl_ctx`
  path; lifting it requires a test framework overhaul.
- Per-listener `accept_thread_func` refactor (already on
  remote workstream as v0.5.42).
- Concurrent graceful-shutdown test (framework timing
  issue).
- TLS 1.3 session ticket resumption test (server does not
  issue tickets; defer to a future round that adds ticket
  issuance).
- Retain-file migration from the pre-v0.5.84 two-length
  format to the v0.5.84 single-length format.
- mTLS + ALPN combined.
- Session-cache hit correctness on the initial CTX.
- Underlying session-cache correctness — the v0.5.73 test
  only accepts `reused == 0` or `reused == 1`; a future
  round (v0.5.90+) should fix the cache and tighten the
  assertion.
