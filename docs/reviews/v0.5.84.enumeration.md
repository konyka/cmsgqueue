# v0.5.84 — MQTT retain file: read/write loop bug + format cleanup

## Scope

v0.5.84 closes a critical production bug in the MQTT retain
file persistence path AND cleans up the on-disk format.

### Bug 1 (CRITICAL): read/write loop in cmq_mqtt_set_retain_path

The pre-v0.5.84 implementation of `cmq_mqtt_set_retain_path`
read each entry from the file and called
`cmq_mqtt_store_retained` to populate the in-memory store.
`cmq_mqtt_store_retained` checks `g_mqtt_retain_path[0]` and
appends the entry to the file if set. The reader set
`g_mqtt_retain_path` BEFORE the read loop, so each call to
`cmq_mqtt_store_retained` from inside the loop re-appended
the entry to the same file. The fscanf loop then read the
newly-appended entry and called store_retained again, and so
on, infinitely.

In production, this means a server that boots with an
existing retain file hangs at startup. The bug was latent
because the v0.5.43 retained test did not exercise the
file-load path (it only used in-memory storage).

The v0.5.84 fix: clear `g_mqtt_retain_path` before the read
loop, restore it on the way out. While `g_mqtt_retain_path`
is empty, `cmq_mqtt_store_retained` skips the file write.

### Cleanup: on-disk format duplicated a length field

The pre-v0.5.84 writer at
`src/enterprise/cmq_mqtt_server.c::cmq_mqtt_store_retained`
wrote `"%s %d %zu "` — the topic followed by both
`(int)payload_len` and `len`. The two values were always
identical (line 611 sets `payload_len = len`), so the
duplication was harmless. The reader parsed both into
`tlen` and `plen`, with `tlen` misnamed (it was payload
length, not topic length). v0.5.84 cleans the format to
`"%s %zu "` (single length) and the reader to `%127s %zu `.

The format change is NOT backward-compatible: an old-format
file (with the duplicate length) is no longer readable
by the new reader (it would only consume the first
length, then try to fread the second number as bytes,
failing). For deployments with existing retain files,
the user must clear the file before upgrading. v0.5.84
ships without migration logic; new deployments start
with the clean format.

## What v0.5.84 ships

### Production fix (`src/enterprise/cmq_mqtt_server.c`)

- **`cmq_mqtt_set_retain_path`**: clear
  `g_mqtt_retain_path` before the read loop, restore on
  the way out. Prevents the read/write loop that hung
  server startup.
- **`cmq_mqtt_store_retained`**: change the file format
  from `topic <payload_len> <len> <payload>\n` to
  `topic <len> <payload>\n`. Single length field.
- **`cmq_mqtt_set_retain_path` (reader)**: change the
  fscanf format from `%127s %d %zu ` to `%127s %zu `
  to match the new writer.

### New test file (`tests/test_mqtt_retained_file.c`)

- **`mqtt_retained_file, file_format_text`**: stores a
  retained message, then directly inspects the on-disk
  file. Verifies the line starts with the topic followed
  by a single digit (length), a space, and the payload.
  Catches regressions where the writer reintroduces a
  duplicate length.
- **`mqtt_retained_file, roundtrip_via_set_path`**: stores
  a message, then re-calls `cmq_mqtt_set_retain_path` to
  simulate a server restart. Verifies the message comes
  back via `cmq_mqtt_fetch_retained` with the same
  payload. Catches the read/write loop bug (the test
  would hang forever without the production fix).

### Port fix (folded in from v0.5.83)

- **`tests/test_tls_e2e_handshake.c::alpn_no_overlap_rejected`**:
  port 25580 → 25581. v0.5.80's `tls_cert_without_key_rejected`
  uses 25580 (but doesn't actually bind, so there's no
  runtime conflict); v0.5.84 moves v0.5.83's test to 25581
  to make the per-test port usage unambiguous in the source.
