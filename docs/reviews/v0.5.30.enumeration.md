# v0.5.30 — Per-config TLS cache isolation test

## Scope
v0.5.18 ships a multi-listener runtime that can bind multiple ports.
v0.5.27 wires the session cache into the per-listener SSL_CTX. The
natural next question: are per-listener caches isolated?

Today's reality: `cmq_server_t` only ever creates `tls_config_slots[0]`
(see cmq_server.c:6910). Slots 1-3 are reserved in the struct but
not allocated. So multi-listener TLS isn't deployed yet.

v0.5.30 ships a test that proves the **lower-layer invariant**: when
two `cmq_tls_config_t` instances coexist, their caches are isolated.
Specifically:

- A session generated for config A must NOT be retrievable via
  config B's cache.
- The new_session callback on each CTX must reference its own cfg
  (verified via SSL_CTX_get_app_data).
- Independent handshakes through each cfg must populate each cache
  independently.

This is the precondition for the future per-listener TLS work.

## Design (performance-first, safety, reliability)

### Test structure

- Two `cmq_tls_config_t` instances (cfg_a, cfg_b), each loaded with
  the same self-signed cert.
- Each has its own session cache (independent state).
- A real handshake via cfg_a populates cfg_a's cache.
- A real handshake via cfg_b populates cfg_b's cache.
- After both, sizes are independent (cache_a = 1, cache_b = 1).
- Direct lookup test: insert a session into cfg_a with a known ID;
  verify cfg_b does not find it.

### Safety

- Both configs use the same cert (no real key conflict).
- All fds explicitly closed in teardown.
- 5s budget per handshake.

### Reliability

- select() loop bounded at 200 iters × 10ms = 2s per handshake.
- Test is deterministic; no time-of-day dependencies.

## Risk
- Low risk. The cache module is per-cfg by construction (it
  uses a pointer stored on the cfg via accessor functions). Two
  configs have two cache state pointers → no cross-talk.
