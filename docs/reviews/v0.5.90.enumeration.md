# v0.5.90 — mTLS + ALPN combined handshake

## Scope

v0.5.90 adds a defensive test that locks in the combination
of mTLS (TLS client certificate authentication) and ALPN
protocol negotiation on the same listener. The existing
test suite has 5 mTLS tests and 4 ALPN tests, but no test
exercises both at once.

The combination is real-world production: HTTPS endpoints
that require client certificates AND negotiate HTTP/2 (or
another ALPN protocol) for legitimate clients. A regression
that broke either subsystem would not surface in either
test alone; both must work together for the handshake to
succeed.

## What v0.5.90 ships

### Defensive test

(`tests/test_tls_e2e_handshake.c`):

- **`tls_e2e_handshake, mtls_alpn_combined`**:
  - Spins up a server with both mTLS (verify_peer=1, tls_ca
    set) and ALPN ("h2,nats") on port 25586.
  - Connects a client with both a valid client certificate
    AND ALPN ("nats,h2").
  - Asserts the handshake completes (`drive_handshake_with_client_cert`
    returns 1).
  - Asserts `SSL_get0_alpn_selected` returns "h2" (the
    server's first preference), proving both subsystems
    worked in combination.

Catches regressions:

- A future change to `cmq_tls_alpn_select_cb` that
  breaks under mTLS (e.g., assumes app_data is always
  set without a CA bundle, or breaks when verify_peer=1).
- A future change to `cmq_tls_sess_get_cb` that breaks
  when ALPN is configured.
- A future change to the certificate chain validation
  that drops the ALPN extension before the cert chain is
  validated, or vice versa.

## Why this matters

mTLS and ALPN are both standard features on production
TLS endpoints. Many real deployments use both: enterprise
APIs that authenticate clients with certificates AND
prefer HTTP/2 over HTTP/1.1. A regression that breaks one
when the other is configured is a silent outage for those
deployments.

The combined test also exercises the interaction between
the ALPN select callback (`cmq_tls_alpn_select_cb`) and
the cert verification path: in TLS 1.3, the server sends
the CertificateRequest AFTER the EncryptedExtensions (which
contains ALPN). A regression in OpenSSL handling could
break this ordering in subtle ways.

## Deferred (unchanged)

- TLS 1.3 mTLS via post-handshake auth. The TLS 1.2 cap
  remains in place for the initial `tls_build_ssl_ctx`
  path; lifting it requires a test framework overhaul.
- Per-listener `accept_thread_func` refactor (already on
  remote workstream as v0.5.42).
- Concurrent graceful-shutdown test (framework timing
  issue).
- TLS 1.3 session ticket resumption test (server does not
  issue tickets).
- Retain-file migration from the pre-v0.5.84 two-length
  format to the v0.5.84 single-length format.
- Session-cache hit correctness on the initial CTX.
- Underlying session-cache correctness — the v0.5.73 test
  only accepts `reused == 0` or `reused == 1`; a future
  round should fix the cache and tighten the assertion.
