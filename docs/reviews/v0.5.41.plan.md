# v0.5.41 — F2 BATCH compression wire-up

## Goal

Make the advertised zstd BATCH codec actually work, without reopening
the F11 interop bug (compressed PUBLISH fanned out as garbage) and
without a decompression-bomb allocator.

## Why this first

INFO already says `"compression":"zstd"`. `handle_batch` already has
a decompress branch. The parser still fail-closes every compressed
frame. That is a correctness + security lie: clients that negotiate
the codec get torn down; the unused handler also sizes the dest
buffer from `ZSTD_compressBound(compressed_len)`, which is not the
uncompressed size.

Other gaps (second accept thread, MQTT 5.0 property decode, OTel,
JetStream) are catalogued in `v0.5.41.enumeration.md`. They are
larger or orthogonal. This round is one closed loop.

## Design (performance-first, safe, reliable)

### Parser (fail-closed except BATCH)

In `cmq_parser_feed`, replace the unconditional COMPRESSED reject
with:

```
if (flags & COMPRESSED && op != BATCH) pending_error = 1;
```

PUBLISH / MESSAGE / REQUEST keep the F11 reject. BATCH proceeds;
`handle_batch` is the only consumer.

Cost: one compare, and only when bit 0 is set. Uncompressed 64 B
frames stay on the existing path (flag bit clear → no extra work).

### Dest size (bomb-safe)

Add `cmq_decompress_bound(src, src_len)`:

1. `ZSTD_getFrameContentSize` — O(1) header peek. No allocation.
2. Reject `UNKNOWN` and `ERROR` (fail-closed; no unbounded decode).
3. Reject size `0` or `> 16 MiB`.
4. Return the exact content size.

`handle_batch` then `malloc(bound)` and `cmq_decompress(..., bound)`.
ZSTD still refuses to write past `dst_cap`.

**No 16× ratio cap.** A 4 KiB JSON payload at zstd-1 is ~30 B
(~130×). A 16× ratio would reject the documented happy path. The
bomb bound is the 16 MiB hard cap plus a known content size (we
never allocate more than the header claims, and never more than
16 MiB).

### Recursion / flags

After decompress, recurse into `handle_batch` with the decoded
buffer and **clear** `CMQ_FLAG_COMPRESSED` on the local frame so a
corrupt inner flag cannot recurse. One level only.

### Checksum + compress

`COMPRESSED|CHECKSUM` on BATCH is accepted by the parser. If the
trailing CRC is still attached, zstd fails and the client gets
`compressed batch rejected`. Fail-closed; no new checksum-strip
in this round (F3 stays on PUBLISH).

## Performance budget

- Uncompressed publish path: unchanged (flag bit clear).
- Compressed BATCH: one header peek + one exact-size malloc +
  zstd-1 decompress (~1 µs / 4 KiB) + existing fan-out.
- Floor: ≥ 25 000 msg/s, p99 ≤ 200 µs on the canonical bench
  (`docs/adr/0017-perf-regression-gate.md`).

## Security

- Per-message COMPRESSED still rejected (F11).
- Unknown / oversize zstd content size → reject, no alloc.
- 16 MiB allocation ceiling.
- Corrupt zstd → error, connection stays (existing ERROR frame);
  parser fatal is reserved for non-BATCH COMPRESSED.

## Reliability

- Empty or truncated BATCH after decompress still hits the
  existing `payload_len < 2` / pass-1 validation (no partial
  fan-out).
- Recursion clears the flag; no decompress loop.
