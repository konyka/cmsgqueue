# v0.5.33 — Wire srv_find_tls_slot into accept_cb

## Scope
v0.5.32 added `srv_find_tls_slot` and the `client->tls_slot` field,
but the accept path still uses slot 0 for every connection.
v0.5.33 wires it up: after `cmq_client_create`, the accept
callback sets `client->tls_slot = srv_find_tls_slot(srv, listen_fd)`,
and `client_tls_handshake` reads `client->tls_slot` to pick the
right `tls_config_slots[i]`.

## Design (performance-first, safety, reliability)

### Changes

1. In `accept_cb`, after `cmq_client_create` returns (both worker
   path at line 6482 and legacy path at line 6530), set
   `client->tls_slot = srv_find_tls_slot(srv, fd)`. The `fd` arg
   of `accept_cb` is the listen fd that fired; the helper does a
   linear scan over `listen_fds[]` and returns the matching index.

2. In `client_tls_handshake`, replace `srv->tls_config_slots[0]`
   with `srv->tls_config_slots[client->tls_slot]`. Bounds-check the
   index: if it's out of range or the slot is NULL, return 0 (no
   handshake) — the client stays plaintext.

3. The `accept_thread_func` (v0.5.17 stub) is unchanged. It doesn't
   go through the worker pipeline yet; its slot selection is a
   future work item.

### Safety

- `client->tls_slot` is set BEFORE `client_tls_handshake` is called
  in the same thread, so no atomic needed.
- The slot index is bounded by the lookup function (returns 0–3
  or 0 on miss). `client_tls_handshake` does an explicit
  range check before indexing, defensive against future
  `CMQ_MAX_LISTENERS` growth.
- If a listener has no TLS config (slot is NULL), the helper
  still returns its index, but `client_tls_handshake` returns
  0 (no handshake). Plaintext connection proceeds normally.

### Reliability

- No new failure modes. The existing `if (!srv->tls_config_slots[0])`
  check is replaced by a per-slot check, same behavior.

## TDD phases
1. **Red**: the v0.5.32 test (`srv_find_tls_slot_lookup`) is
   unit-level. For v0.5.33 the existing tests pass (because
   `client->tls_slot` defaults to 0, matching the prior
   hard-coded slot 0 behavior). A real integration test would
   require running a TLS handshake against two distinct listener
   certs — brittle, deferred (covered in v0.5.32 honest caveats).
   So v0.5.33 is a **code change without a new test**: the
   refactor is verifiable by reading the diff. Existing tests
   must continue to pass.
2. **Green**: apply the changes. Existing tests pass.
3. **Verify**: full ctest, bench.

## Risk
- Low. The refactor is mechanical: set a field, read a field.
  Behavior change is zero for single-listener deployments
  (slot 0 is the default). Multi-listener behavior was previously
  "always use slot 0" and is now "use the slot matching the
  listen fd" — which is the documented intent.
