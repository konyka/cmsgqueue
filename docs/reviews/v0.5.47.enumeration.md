# v0.5.47 — CRL revocation plumbing in cmq_server config

## Scope

The CRL (Certificate Revocation List) feature has been
implemented inside `cmq_tls.c` since v0.5.2 — `cmq_tls_set_crl`
sets `cfg->crl` and `tls_build_ssl_ctx` loads it into the
SSL_CTX's X509_STORE. But `cmq_server_create` never calls
`cmq_tls_set_crl`, and `cmq_config_t` has no `tls_crl` field.
The CRL API is unreachable from the server's public config.

v0.5.47 closes this gap:
1. Adds `const char *tls_crl` to `cmq_config_t`.
2. Wires it through `cmq_server_create` for both the legacy
   slot 0 and the per-listener slots.
3. Adds an end-to-end test that generates a CA, a client cert,
   revokes the client cert, and verifies the server rejects
   the now-revoked client during the mTLS handshake.

## Design

### Config field

```c
/* In cmq_config_t, next to tls_ca: */
const char *tls_crl;       /* v0.5.47: CRL file for client cert revocation check. */
```

### Wiring in cmq_server.c

```c
/* After the existing tls_ca wiring: */
if (srv->config.tls_crl) {
    cmq_tls_set_crl(srv->tls_config_slots[0], srv->config.tls_crl);
}
/* Same for listeners[i] */
```

### Test flow

`tests/test_tls_e2e_handshake.c::mtls_revoked_client_rejected`:

1. Generate a CA + server cert + client cert (same as v0.5.46).
2. Generate a CRL that revokes the client cert:
   `openssl ca -gencrl -revoke client.pem -out crl.pem`
3. Configure `cmq_server` with `tls_verify_peer=1`,
   `tls_ca=ca.pem`, `tls_crl=crl.pem`.
4. Connect with the client cert → handshake must FAIL
   (revoked cert → X509_V_ERR_CERT_REVOKED).

Without the v0.5.47 wiring, the CRL is never loaded and the
revoked cert would be accepted (sub-test fails). With it,
the server rejects the revoked cert (sub-test passes).

## Safety

- `cmq_tls_set_crl` is already hardened: NULL path is a no-op,
  bad path is logged + skipped (no false rejections from a
  bad CRL file).
- The config field defaults to NULL → existing deployments
  unchanged.
- Per-listener CRL support mirrors the existing per-listener
  tls_ca support.

## Performance

- Zero impact on the plaintext path.
- mTLS path: CRL is loaded once at server start; per-handshake
  cost is a single O(1) X509 store lookup against the revoked
  serial number.
- Bench: ~33K msg/s end-to-end, p99 99.0 µs (unchanged).

## Test framework

- Certs + CRL generated via openssl CLI (same pattern as
  v0.5.46 mtls_required).
- CRL generation requires a CA database (`./index.txt`,
  `./serial`). The test creates these in `/tmp/cmq-test-v0547/`.
- Existing `drive_handshake_with_client_cert` is reused; no
  helper changes needed (CRL check is synchronous during
  verify_peer, so a TLS 1.2 cap + verify_peer handshake is
  sufficient).

## Risk

- CRL generation has many small failure modes (CA database
  must be initialized; serial number must exist). Mitigate by
  asserting every step (check file existence, check CRL
  contains the expected serial).
- The test uses TLS 1.2 (because of the v0.5.46 cap); CRL
  behavior on TLS 1.3 mTLS is gated by the TLS 1.3 mTLS path
  (which is v0.5.48+). Document this in the test header.
