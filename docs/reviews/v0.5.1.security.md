# CMSGQueue v0.5.1 — Security & Reliability Review

Scope: audit log rotation (F2), WAL replay (F5), F17 BIO-wrap integration,
mTLS client cert chain, server-side per-subject rate limit, and
thread-safety/race audit. Findings are risk-focused with concrete fixes.

## 1. WAL replay is a silent no-op (data-loss risk)

- **Area:** F5 replay, `cmq_server_create` → `handle_publish`
- **Risk:** CRITICAL (every persisted message is dropped on restart)
- **File:line:** `src/server/cmq_server.c:6672-6684` (replay client build),
  `cmq_server.c:2817` (account-live gate), `cmq_server.c:6567` (`$default`
  created with `epoch=1`)
- **Analysis:** `replay_c` is zeroed then only `account_name` and `server`
  are set. `account_epoch` stays 0, but the `$default` account is created in
  `cmq_server_create` with `epoch=1`. `handle_publish` calls
  `client_account_live()` first, which requires
  `ep == c->account_epoch && aep == c->account_epoch`; `(1==0)` is false, so
  **every** replayed record is rejected with "account inactive" and never
  reaches sublist delivery or the WAL append. The feature logs
  "Replaying N WAL records … complete" and reports success while silently
  discarding the entire backlog.
- **Latent second bug:** if the epoch check is naively fixed (e.g. by
  stamping the current `$default` epoch), `handle_publish` will re-persist
  each record via `cmq_filestore_append` (line 2940). `last` is snapshotted
  before the loop, so duplicates land at `seq > last` and are replayed on the
  **next** restart — unbounded WAL growth plus duplicate delivery.
- **Fix:** (a) give `replay_c` a valid `account_epoch` (read the live
  `$default` epoch at replay time) and an internal "replay" flag;
  (b) in `handle_publish`, skip the WAL append when the replay flag is set
  (persistence is the record source, not a sink); (c) set `fd = -1` and
  `worker_id = -1` so any error path can't `write()` to fd 0 (stdin) —
  today a rejected record falls through `cmq_client_send_direct` →
  `cmq_ev_mod(NULL, 0, …)` → one-shot drain → `write(0, …)`.
## 2. Per-subject rate limit is not thread-safe and bypassable

- **Area:** N1 `cmq_subject_rl.c` + `handle_publish`
- **Risk:** HIGH (limit bypass; heap corruption on bucket list)
- **File:line:** `src/server/cmq_subject_rl.c:40-53` (`find_or_create`),
  `cmq_subject_rl.c:55-69` (`cmq_subject_rl_check`), `cmq_server.c:2967`
- **Analysis:** `handle_publish` runs concurrently on N worker threads.
  `cmq_subject_rl_check` has **zero** synchronization: `find_or_create`
  mutates the singly-linked `buckets` list (`b->next = rl->buckets;
  rl->buckets = b`) without a lock, so two workers can create two buckets for
  the same subject, or lose a node / loop the list. The check-then-increment
  (`if (b->count >= max) return 0; b->count++;`) is non-atomic, so the limit
  is undercounted under concurrency → bypass. `cmq_quota_check_publish`
  (`src/enterprise/cmq_quota.c:40-52,65-81`) has the identical race.
- **Fix:** protect `cmq_subject_rl_check` (and `cmq_quota_check_publish`)
  with a mutex or switch to an atomic fixed-slot hash (slots are already
  declared: `CMQ_SUBJECT_RL_SLOTS 4096` is unused). Use
  `__atomic_fetch_add` with a CAS on window reset for the counter.

## 3. N1/F14/F16 enforcement bypassed via BATCH and persists rejected messages

- **Area:** `handle_batch` vs `handle_publish`
- **Risk:** HIGH (rate limit / ACL / quota evasion)
- **File:line:** `src/server/cmq_server.c:4037-4105` (`handle_batch`),
  `cmq_server.c:2940` (append before checks)
- **Analysis:** `handle_batch` (up to `CMQ_BATCH_MAX=256` messages per frame)
  only runs `cmq_account_can_export` per subject. It never calls
  `cmq_acl_check`, `cmq_quota_check_publish`, or `cmq_subject_rl_check`, so a
  client can trivially bypass all three limits by sending a BATCH frame.
  Additionally, in `handle_publish` the WAL append (2940) happens **before**
  the ACL/quota/rate checks (2952/2960/2968), so denied publishes are still
  persisted to the WAL — and would be re-delivered by any future working
  replay.
- **Fix:** apply the same ACL/quota/subject_rl gates per entry in
  `handle_batch` pass 1; move the WAL append after all admission checks (or
  append only on accept).

## 4. mTLS client-cert chain is never enforced

- **Area:** F12 `cmq_tls.c` + server wiring
- **Risk:** HIGH (mTLS feature is dead; client identity is not verified)
- **File:line:** `src/enterprise/cmq_tls.c:95-140`
  (`tls_build_ssl_ctx`), `cmq_tls.c:293-295` (verify set only in `reload`),
  `cmq_server.c:6608` (server calls only `cmq_tls_load`)
- **Analysis:** `tls_build_ssl_ctx` (used by `cmq_tls_load` and the lazy
  session path) loads the CA store (line 138) but **never calls
  `SSL_CTX_set_verify`**, so OpenSSL does not request or validate a client
  certificate. The only code that sets `SSL_VERIFY_PEER |
  SSL_VERIFY_FAIL_IF_NO_PEER_CERT` is `cmq_tls_reload` (293-295), which the
  server never calls. `cmq_tls_set_ca` / `cmq_tls_set_verify` are invoked
  only from tests. There is also no config key for CA/verify, so mTLS is
  unreachable in production. Additionally, `cmq_tls_reload` calls
  `SSL_CTX_free(old)` immediately after the swap while live `SSL*` objects
  still reference the old CTX (OpenSSL does not ref-count the CTX in
  `SSL_new`), so any future hot reload is a use-after-free.
- **Fix:** in `tls_build_ssl_ctx`, apply the same
  `SSL_CTX_set_verify(SSL_VERIFY_PEER | SSL_VERIFY_FAIL_IF_NO_PEER_CERT)`
  when `verify_peer` is set; wire `set_ca`/`set_verify`/reload into
  `cmq_server_create` (add `tls_ca` / `tls_verify_peer` config keys); defer
  freeing the old CTX until its sessions drain (refcount or generation list).

## 5. F17 route TLS is dead code; if wired it would deadlock

- **Area:** F17 `cmq_route.c` + `cmq_route_tls_sess.c`
- **Risk:** MEDIUM (false sense of security + latent blocking I/O)
- **File:line:** `src/cluster/cmq_route.c:194-199` (`write_full`),
  `cmq_route.c:175-186` (helpers), `cmq_route_tls_sess.c:15-32`
- **Analysis:** No production code calls `cmq_route_tls_sess_create`,
  `cmq_route_tls_config_*`, or `cmq_route_tls_available`; `write_one` /
  `read_one` are only invoked with `sess=NULL` from `cmq_peer_handshake`.
  The hot broadcast path (`write_full`, used by `cmq_route_broadcast`) still
  calls raw `write()` and never consults a session — the claimed "BIO-wrap
  write_full/read wiring" is not on the delivery path. There is no per-slot
  `cmq_route_tls_sess_t` in `cmq_route_conn_t`, and `cmq_route_tls_config_t`
  is a disconnected struct that never builds a session. If wired, the
  implementation would be unsafe: `cmq_route_tls_sess_create` performs a
  blocking `SSL_do_handshake` with no timeout and no `O_NONBLOCK`, and
  `sess_read/write` use raw `SSL_read/SSL_write` on a blocking fd — a stalled
  peer would hang a worker or the reconnect thread indefinitely, and a
  partial `SSL_write` (no `SSL_MODE_ENABLE_PARTIAL_WRITE`) would return
  `WANT_WRITE` on a blocking fd.
- **Fix:** store the session in `cmq_route_conn_t` guarded by `io_locks[idx]`
  and route `write_full` through `write_one`; make handshake and reads
  non-blocking with poll timeouts; enable partial-write mode; add a
  `route_require_tls` config key and an integration test that actually
  exercises the TLS session on both sides.

## 6. Reload races (ACL + blocklist use-after-free)

- **Area:** `cmq_server_reload` vs worker readers
- **Risk:** HIGH (UAF reachable through the public `cmq_server_reload` API)
- **File:line:** `src/server/cmq_server.c:7157-7190`,
  `cmq_server.c:2952` (ACL reader), `cmq_server.c:4435` (blocklist reader)
- **Analysis:** `cmq_server_reload` frees `server->acl` and swaps it with no
  lock (7187-7188), while worker threads call `cmq_acl_check(srv->acl,…)`
  lock-free (2952). The blocklist swap takes `rate_lock` but frees the old
  object **after** releasing the lock (7160-7164), and the reader at 4435
  does not hold `rate_lock` — a reader that loaded the old pointer can use it
  after free. The `cmq_blocklist_check` comment claiming "accept_cb is the
  only caller" is stale (handle_frame CONNECT also calls it from workers).
- **Fix:** guard `acl` and `blocklist` pointer loads with an atomic or a
  dedicated mutex shared by readers and the reload path; free the old object
  only after it can no longer be observed (e.g. deferred free via refcount /
  epoch check, same pattern as `tls_begin_op`).

## 7. Audit log rotation is non-functional

- **Area:** F2 audit rotation
- **Risk:** MEDIUM (audit file never rotates; silent loss on failure)
- **File:line:** `src/enterprise/cmq_audit.c:81-94`
- **Analysis:** (a) no production code calls `cmq_audit_set_path` — the
  server has no config key for the audit path, so events go to stderr only
  and rotation is unreachable; (b) even with a path set, the rotation check
  uses `ftell(f)` after `fopen(path,"a")`+`fputs` — the stream is reopened on
  every event, so `ftell` measures only the current line, never the file
  size, and the 100 MiB threshold can never trip; (c) `fopen` failure is
  silently ignored, so ENOSPC/permissions drop the trail without an error;
  (d) `rename` over `path.1` discards the previous rotation and the
  directory is never fsynced, so a crash can lose the rotated file.
- **Fix:** keep a persistent `FILE*` (open once), check file size via
  `ftello`/`fstat` on the open stream, and rotate to a timestamped name with
  `fsync` on the directory; surface open/write failures (audit counter +
  log). Wire the path from config.

## 8. Dead enforcement paths (connect quota, audit events)

- **Area:** `cmq_quota_check_connect`, `CMQ_AUDIT_*`
- **Risk:** LOW-MEDIUM (documented limits silently not enforced)
- **File:line:** `src/enterprise/cmq_quota.c:84`,
  `src/enterprise/cmq_audit.h:22-29`, `cmq_server.c:4436`
- **Analysis:** `cmq_quota_check_connect` is never called, so
  `max_connections_per_account` is dead despite being advertised. Only one
  audit event (`rate_limit_reject` used for blocklist) is emitted; the
  `auth_ok`, `auth_fail`, `persist_fail`, and `tls_handshake_fail` events in
  the enum are never produced, so the audit trail is nearly empty.
- **Fix:** call `cmq_quota_check_connect` in the CONNECT path; emit the
  remaining audit events at their natural call sites.
