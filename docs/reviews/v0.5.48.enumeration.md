# v0.5.48 — TLS 1.3 mTLS investigation: cap stays, deferred to v0.5.49+

## Scope

v0.5.46 capped the SSL_CTX at TLS 1.2 when `verify_peer` is set,
because OpenSSL 3.5 + TLS 1.3 silently bypasses
`SSL_VERIFY_FAIL_IF_NO_PEER_CERT`. v0.5.48 investigated whether
the cap can be lifted by wiring the proper TLS 1.3 client-cert
post-handshake auth path.

## What was tried

1. **`client_hello_cb`** in `tls_build_ssl_ctx` (installed only
   when `verify_peer=1`) calls:
   - `SSL_set_verify(ssl, SSL_VERIFY_PEER |
     SSL_VERIFY_FAIL_IF_NO_PEER_CERT, NULL)` per-SSL on every
     ClientHello — forces the per-SSL verify mode that the
     server-side path needs.
   - `SSL_verify_client_post_handshake(ssl)` — schedules the
     post-handshake CertificateRequest exchange.

2. **`info_cb`** watches for `SSL_CB_ALERT` with description
   `SSL3_AD_HANDSHAKE_FAILURE` (40), `SSL3_AD_BAD_CERTIFICATE`
   (42), or `SSL3_AD_CERTIFICATE_REVOKED` (44). Sets
   `session->handshake_failed = 1` so the event loop can tear
   down the client on the next wakeup.

3. **`cmq_tls_flush`** new public API: wraps `SSL_write(NULL, 0)`
   which forces OpenSSL to flush pending records (notably the
   post-handshake CertificateRequest on TLS 1.3). The
   application must call this after `handshake_done` for the
   post-handshake exchange to begin.

4. **`cmq_tls_handshake_failed`** new public API: returns 1 if
   the info callback detected a cert-verification failure alert.
   The event loop reads this on the next wakeup and tears down
   the client.

5. **Server event loop change**: after the v0.5.45 read-path
   resume completes (`handshake_done`), call `cmq_tls_flush` to
   trigger the post-handshake CertificateRequest. Then check
   `cmq_tls_handshake_failed`; if set, immediately shutdown the
   fd and call `client_teardown`.

## What broke

The full integration test (`mtls_required` + `mtls_revoked_client_rejected`)
exposed a race condition: with the cap lifted, **authenticated
mTLS clients** (sub-test A of `mtls_required`) were torn down
prematurely after the post-handshake CertificateRequest was
sent. The client successfully presented its cert, the server
verified it (no alert), but the connection still got torn down
within ~5ms of the post-handshake exchange.

Root cause investigation: the post-handshake exchange involves
multiple `SSL_do_handshake` calls returning `WANT_READ` /
`WANT_WRITE`. The server's `client_read_cb` and `client_flush_write`
both drive these calls. But the v0.5.45 read-path resume fires
on every EV_READ, and `cmq_tls_flush` (the new v0.5.48 path)
also fires on EV_WRITE. The interaction between the post-handshake
state machine and the v0.5.45 resume path produces a race where
the SSL enters an error state on an authenticated client.

Likely culprits:
- `SSL_verify_client_post_handshake` schedules the
  CertificateRequest but the FIRST `SSL_write` flush only writes
  part of the request; the server's `client_read_cb` then
  processes the client's cert response, but at that point the
  `handshake_done` flag is already true (initial handshake done)
  AND the cert verify hasn't completed yet, leading to a state
  inconsistency.
- The `info_cb` might fire with `SSL3_AD_HANDSHAKE_FAILURE` for
  legitimate reasons unrelated to mTLS (e.g., if the client
  sends unexpected data during the post-handshake flight).

## Resolution

The cap from v0.5.46 stays. **TLS 1.2 mTLS is the only stable
path.** Production deployments requiring mTLS on TLS 1.3 must
accept that the client must opt in to `post_handshake_auth`
(most clients don't), and even then, the race condition makes
silent connection drops possible.

## What v0.5.48 actually ships

Nothing — production code is unchanged from v0.5.47. This
round is documentation-only: enumerates the TLS 1.3 mTLS path,
documents why the cap stays, and points to v0.5.49+ for the
proper fix.

## Deferred to v0.5.49+

- Resolve the post-handshake / read-path race condition. The
  likely fix is to gate the v0.5.45 read-path resume on
  `!handshake_failed` so a failure alert stops further reads.
- Or: defer the `cmq_tls_flush` call until the server's first
  application-level write (instead of firing immediately after
  the initial handshake).
- Investigate whether the SSL's internal state can be queried
  more cleanly (e.g., via `SSL_in_before()` /
  `SSL_in_init()`) to know when the post-handshake exchange
  is actually in progress.
- Consider switching to a TLS 1.3-only design that mandates
  post-handshake auth via the `client_cert_engine` API
  (research pending).
