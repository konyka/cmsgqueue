# v0.5.48 — Per-account concurrent limits

## Scope
D8 from v0.5.41: account objects already count `connections` /
`subscriptions` / bytes, but nothing enforces a NATS-style hard
cap. F14 `cmq_quota_check_connect` is a **per-second connect
rate** (and is still unwired). `max_connections_per_account` stays
that rate knob.

This increment adds **concurrent** connection and subscription
ceilings, plus a per-message payload cap, on `cmq_account_t`.

P3 leftovers (OTel, HTTP/2, JWT, JetStream, EOS, Kafka compact,
subject rewrite) stay deferred. Outstanding-byte memory budgets
are not this version.

## Design (performance-first, safety, reliability)

### Limits on the account, checked in the existing inc

`max_connections` / `max_subscriptions` / `max_payload` live on
`cmq_account_t`. `0` means unlimited: the inc path is one atomic
load + compare, then the same `fetch_add` as today.

When a cap is set, credit uses a CAS loop so two CONNECTs cannot
both sneak past `max_connections`.

### Return codes

- `0` — credit stuck on this epoch
- `-1` — inactive / epoch / clear_gen race (existing)
- `-2` — at the concurrent cap

CONNECT still CONNACK 1 + close on either failure. SUBSCRIBE
sends SUBACK 1 and **stays up** on `-2` (the account is fine;
the client is over quota).

### Defaults vs per-account override

`cmq_account_manager_set_defaults` copies onto **new** slots
(create / ensure). Soft-delete + `create()` of the same name
keeps the previous limits. `cmq_account_set_limits` overrides
one account.

Server knobs: `account_max_connections`,
`account_max_subscriptions`, `account_max_payload`. Applied
before `$default` is created.

### Payload on the publish path

Global `max_payload_size` still wins first. The account cap is
cached on the client at CONNECT (`account_max_payload`) so the
publish hot path is one extra compare when the cap is 0.
