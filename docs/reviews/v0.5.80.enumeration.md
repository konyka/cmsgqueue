# v0.5.80 — tls_cert without tls_key defensive test

## Scope

v0.5.80 adds one defensive test that covers a missing case
in the TLS configuration validation matrix. Existing tests:

- v0.5.61: `tls_enabled_without_cert_rejected` — both `tls_cert`
  AND `tls_key` are NULL/missing → rejected ✓
- v0.5.67: `empty_cert_file_rejected` — `tls_cert` points at
  zero-byte file → rejected ✓
- v0.5.76: `garbage_tls_key_rejected` — `tls_cert` valid,
  `tls_key` points at non-PEM → rejected ✓
- **v0.5.80 (new)**: `tls_cert` set, `tls_key` NULL → rejected ✓

The new test covers the "asymmetric" case — `tls_cert` provided
but `tls_key` missing. v0.5.61 tested the both-NULL case; this
covers the only-one case. Both must reject at startup.

## Test: `tls_e2e_handshake.tls_cert_without_key_rejected`

1. Generate a valid self-signed cert + key pair
   (`TLS_DIR/cert.pem`, `TLS_DIR/key.pem`).
2. `cmq_server_create()` with `tls_enabled=1`, `tls_cert=cert.pem`,
   `tls_key` deliberately not set (NULL).
3. Assert return value is non-`CMQ_OK` and `srv == NULL`.

## What v0.5.80 ships

A regression test only. No production change.

## Verified

- `tests/test_tls_e2e_handshake.c::tls_cert_without_key_rejected` PASS
  (3/3 single runs, total suite 29/29).
- Bench: ~33K msg/s, p99 99 µs (unchanged).

## Why this test guards against regressions

In production, a misconfigured `tls_cert` alone (no `tls_key`) is
a common mistake when operators rotate just one file. The cert
verification path on the wire works, but the server can't
sign handshake messages. The startup check must reject this
asymmetric state clearly rather than fail later at first
handshake.
