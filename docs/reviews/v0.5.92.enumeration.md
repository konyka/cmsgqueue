# v0.5.92 — ALPN client-list duplicate protocol handling

## Scope

v0.5.92 adds a defensive test that locks in the ALPN
server-preference callback's behavior when the client
presents a list containing duplicate protocols. This is
a real-world case: buggy or non-conforming clients may
send duplicate protocol entries, and the server's
callback must handle the list without crashing or
returning the wrong protocol.

The existing 4 ALPN tests cover:
- Positive negotiation (server "h2,nats", client "nats,http" → "nats" wins).
- No overlap (handshake fails with fatal alert).
- 2-element server-preference (reversed order, server wins).
- 3-element server-preference (server's first wins).
- mTLS + ALPN combined.

None tests what happens when the client list has
duplicates. The callback iterates the SERVER list and
returns the first match. Duplicates in the client list
are silently ignored (the callback matches each entry at
most once). This contract is non-trivial: a future
refactor that walks the client list instead and tracks
"already returned" would produce different output for
duplicates.

## What v0.5.92 ships

### Defensive test

(`tests/test_tls_e2e_handshake.c`):

- **`tls_e2e_handshake, alpn_client_list_with_duplicates`**:
  - Server: ALPN "h2,nats" on port 25588.
  - Client: ALPN "h2,h2,nats" (the client's first
    protocol appears twice, then the client's second).
  - Asserts the negotiated protocol is "h2" (server's
    first preference), NOT "nats".

The callback returns the first server-listed protocol
that matches any client entry. With duplicate "h2" in
the client list, the callback still matches "h2" first
because that's the server's first preference. The
duplicate in the client list is silently ignored.

Catches regressions: a future change to
`cmq_tls_alpn_select_cb` that tracks "already-matched"
in the client list would surface this test as a failure
(perhaps by returning "nats" because the second "h2" was
"already used").

## Why this matters

Production HTTP/2 deployments have observed buggy or
malicious clients sending duplicate ALPN protocols. The
server's behavior must be deterministic: the server's
first preference must always win. A regression that
silently accepts a non-preferred protocol because of a
client-side duplicate would degrade the user experience
without obvious cause.

## Deferred (unchanged)

- TLS 1.3 mTLS via post-handshake auth. The TLS 1.2 cap
  remains in place for the initial `tls_build_ssl_ctx`
  path; lifting it requires a test framework overhaul.
- Per-listener `accept_thread_func` refactor (already on
  remote workstream as v0.5.42).
- Concurrent graceful-shutdown test (framework timing
  issue).
- TLS 1.3 session ticket resumption test (server does not
  issue tickets).
- Retain-file migration from the pre-v0.5.84 two-length
  format to the v0.5.84 single-length format.
- Tightening the v0.5.73 and v0.5.87 tests to assert
  `reused == 1` would require disabling tickets on the
  server side via `SSL_OP_NO_TICKET`. Deferred — server
  operators may want tickets in production, so this
  should be a configurable option rather than a forced
  default.
