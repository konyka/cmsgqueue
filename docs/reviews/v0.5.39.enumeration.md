# v0.5.39 — MQTT bridge WAL persistence

## Scope
v0.5.36 made the MQTT bridge relay call `cmq_server_publish` (the
proper fanout path), but it doesn't persist to WAL. v0.5.34's
honest caveat noted this. v0.5.39 closes the loop: the bridge
adapter also writes to the filestore when one is configured, so
bridge-published messages survive a server restart.

## Design

### Wire format

The cmq client publish path stores the full wire-format PUBLISH
frame in the WAL. For the bridge, we don't have a wire frame (the
adapter receives `topic` and `payload` from the relay). We use a
**simpler bridge-specific format** on a separate filestore slot:

```
[magic 4B 'CMQB'] [version 1B 0x01] [topic_len 2B BE] [topic][payload]
```

The magic + version let the recovery loop distinguish bridge records
from client records (future v0.5.40+ adds a recovery path; for now
the bridge records are written and that's it).

### Adapter change

`cmq_bridge_publish_adapter` gains a persist step before the
fanout:

```c
if (g_mqtt_bridge_srv && g_mqtt_bridge_srv->filestore) {
    cmq_filestore_append_bridge(g_mqtt_bridge_srv->filestore,
                                  topic, topic_len,
                                  payload, payload_len);
}
```

`cmq_filestore_append_bridge` is a new filestore API: it builds the
frame and calls `cmq_filestore_append`. The existing `cmq_filestore_last_seq`
continues to work (one seq per append regardless of payload size).

### Safety

- The persist step is best-effort: failure increments
  `stat_persist_fail` and continues with the fanout.
- The bridge adapter takes a borrowed reference to `payload`
  (relay-thread-allocated, freed after the adapter returns).
  The persist step copies the bytes into the filestore's own
  buffer; it doesn't take ownership of `payload`.

### Reliability

- The filestore path is single-threaded (filestore_append holds an
  internal lock). The relay thread and the accept thread can both
  append concurrently; the lock serializes them.
- Recovery is NOT in this round. The bridge records sit on disk
  but won't be replayed until v0.5.40+. Document this honestly.
