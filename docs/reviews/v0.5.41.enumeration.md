# v0.5.41 — Rigorous end-to-end bridge recovery test

## Scope
v0.5.40 verified that `cmq_server_create`'s replay loop processes
bridge records (via `stat_messages_replayed > 0`), but that assertion
also ticks on client-PUBLISH records that fail validation. v0.5.41
ships the rigorous follow-up: persist a subscriber matching the
bridge topic, destroy + recreate, and verify `cmq_sublist_match`
returns the recovered subscriber. This proves the v0.5.40 recovery
path actually called `cmq_server_publish` with the recovered bridge
topic (not just that the replay stat incremented).

## Design

### Test flow

1. Create server A with `persist_dir`.
2. `cmq_sublist_persist_record_sub(srv_a->persist, 1, "v0.5.41/sentinel",
   "user1")` — persist a subscriber for the topic.
3. `cmq_sublist_persist_close(srv_a->persist); srv_a->persist = NULL`.
4. `cmq_mqtt_set_bridge_server(srv_a)` — start the bridge relay.
5. `cmq_mqtt_test_enqueue_bridge("v0.5.41/sentinel", payload, len)` —
   the adapter writes a CMQB record to the filestore.
6. Verify `cmq_filestore_last_seq(srv_a->filestore) == 1`.
7. `cmq_mqtt_bridge_shutdown(); cmq_server_destroy(srv_a)`.
8. Create server B with same `persist_dir`.
9. On startup, the v0.5.37 sublist-recovery loop restores the
   subscriber, and the v0.5.40 bridge-recovery loop dispatches
   the CMQB record via `cmq_server_publish("v0.5.41/sentinel", ...)`.
10. `cmq_sublist_match(srv_b->sublist, "v0.5.41/sentinel", &result)`
    returns `result.count == 1`, confirming the recovered subscriber
    matches the recovered bridge topic.
11. `cmq_server_destroy(srv_b)`.

### Safety

- The test only verifies `cmq_sublist_match` returns 1. Per the
  v0.5.37 honest caveat, recovered subscribers are "ghost" refs
  with `client = NULL`, so no actual delivery happens — the test
  verifies the MATCH path, not the delivery path. Delivery tests
  require a live TCP client (v0.6 scope).
- The bridge persist file and the sublist persist file are
  SEPARATE files (`srv->filestore` vs `srv->persist`). The bridge
  write goes to the filestore; the SUB record goes to the sublist
  file. So `cmq_filestore_last_seq` increments by exactly 1
  (just the bridge record).
