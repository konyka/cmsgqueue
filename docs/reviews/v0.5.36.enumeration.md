# v0.5.36 — cmq_server_publish helper + real bridge fanout

## Scope
v0.5.35 reverted the bridge wiring to no-op because the prior
wiring (`cmq_sublist_insert`) was semantically wrong. v0.5.36
implements the proper publish path: a `cmq_server_publish`
helper that does sublist match + fanout, called by the bridge
relay. This makes the bridge **actually deliver messages** to
subscribers.

## Design (performance-first, safety, reliability)

### `cmq_server_publish` API

```c
/* Publish from a non-client context (e.g., the MQTT bridge relay).
 * subject: subject string (validated, max CMQ_MAX_SUBJECT bytes).
 * payload, payload_len: raw message bytes.
 * account_name: owner account for the publish (used for ACL
 *   re-validation in delivery). The bridge uses a fixed synthetic
 *   name "mqtt_bridge".
 *
 * Returns 0 on success, -1 on error (sublist match OOM, etc.).
 * No delivery failures are surfaced — failed deliveries increment
 * stat_messages_dropped, same as the client-publish path. */
int cmq_server_publish(cmq_server_t *srv, const char *subject,
                       const uint8_t *payload, size_t payload_len,
                       const char *account_name);
```

### Implementation

Extracted from `handle_publish`'s post-validation block (line 3080
onwards, where the sublist match + fanout happens). Skips:
- Wire parsing (only frame-level).
- Account/ACL/quota/rate-limit checks (callers do their own).
- WAL persistence (callers do their own; the bridge may want
  persistence too — see Risk below).
- Client error responses (callers handle errors themselves).
- Route forwarding (callers handle cluster forwarding).

What we keep:
- `cmq_sublist_match` — matches subject against the trie.
- `snapshot_deliver_targets` — collects delivery targets.
- `deliver_targets_sync` — synchronous fanout (no coroutine).
- Sublist result cleanup.

### Bridge wiring

`cmq_server_create` (or `cmq_mqtt_set_bridge_server`) registers a
helper that wraps `cmq_server_publish` and hands it the relay
payload + topic. Specifically:

```c
/* Defined in cmq_mqtt_server.c, registered by cmq_server_create. */
static int cmq_bridge_publish_adapter(void *sublist, const char *topic,
                                       void *data) {
    (void)sublist;
    cmq_server_t *srv = g_mqtt_bridge_srv;
    if (!srv) { free(data); return 0; }
    int rc = cmq_server_publish(srv, topic, data, payload_len,
                                  "mqtt_bridge");
    free(data);  /* relay malloc'd; bridge owns the buffer */
    return rc == 0 ? 0 : -1;
}
```

The bridge calls `cmq_mqtt_register_sublist_insert(cmq_bridge_publish_adapter, NULL)`.
The adapter's `free(data)` is correct: the bridge allocates the
payload, publishes it (cmq_server_publish copies or transfers as
needed), then frees the original buffer.

Wait — `cmq_server_publish` should NOT take ownership (it's just
borrowing for delivery). The relay thread's malloc is freed by the
adapter. Good.

### Safety

- The bridge no longer pollutes the sublist (v0.5.35 fix holds).
- `cmq_server_publish` doesn't persist to WAL — the cmq publish
  flow normally does. The bridge intentionally skips persistence
  for now (deferred to v0.6: bridge persistence policy). The
  alternative (persist everything that comes through the bridge)
  is high-volume and may not be desired for bridge use cases.
- `account_name="mqtt_bridge"` is a fixed synthetic. Subscribers
  see this on received messages. Future work could make it
  configurable.

### Reliability

- The helper reuses the existing sublist match + fanout code that
  handle_publish already exercises via 85+ tests.
- The bridge adapter is small (~10 lines) and goes through the
  same path. End-to-end test verifies a subscriber receives a
  message that the bridge relay forwarded.

## Risk
- The bridge now uses CPU and bandwidth to deliver to all matching
  subscribers. Under high MQTT PUBLISH rates this is significant.
  Mitigations (rate limiting, fanout budgets) are v0.6.
- The bridge doesn't persist to WAL. If the server restarts, the
  last few in-flight MQTT publishes are lost. Document as a known
  limitation; persist-by-bridge is a separate opt-in feature.
