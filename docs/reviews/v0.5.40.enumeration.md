# v0.5.40 — Bridge WAL recovery

## Scope
v0.5.39 added `cmq_filestore_append_bridge` so the bridge persists
its PUBLISHes to the WAL. v0.5.40 closes the loop: on
`cmq_server_create`, the replay loop detects `CMQB` records and
dispatches them via `cmq_server_publish` instead of
`handle_publish`. A server restart now replays bridge-published
topics to any matching live subscribers, just like client-PUBLISH
records.

## Design (performance-first, safety, reliability)

### Detection

`replay_one_record` peeks at the first 4 bytes of the record:
- If they equal `"CMQB"` (the bridge magic from v0.5.39), it's a
  bridge record.
- Otherwise, treat as a client PUBLISH record (existing path).

### Bridge record parsing

Bridge frame layout (from v0.5.39):
```
[magic 4B 'CMQB'] [version 1B 0x01] [topic_len 2B BE]
[topic] [payload]
```

`topic_len` is `uint16_t big-endian`. Validation:
- `data_len >= 7` (4 + 1 + 2 minimum).
- `topic_len > 0`.
- `topic_len + 7 <= data_len` (room for topic + at least 0 bytes payload).
- Reject if version != 0x01 (forward-compat: unknown version = drop).
- Reject if topic contains NUL (cmq subjects are C strings).

### Dispatch

`cmq_server_publish(srv, topic, payload, payload_len, "mqtt_bridge_replay")`
dispatches the recovered message. The `cmq_server_publish` path
(v0.5.36) does sublist match + sync fanout; no wire parsing, no
ACL/quota/rate-limit checks. Recovery-time publishes skip those
checks because the original publish already passed them.

### Counter

Increment `stat_messages_replayed` (existing field) by 1 for each
recovered bridge record. Split out a new counter
`stat_messages_bridge_replayed` (or reuse `stat_messages_replayed`
with a flag) — for now, share the existing counter. v0.6 can
split if stats granularity is needed.

### Safety

- Recovery is bounded by `cmq_filestore_last_seq`; the loop
  doesn't run if the WAL is empty.
- A corrupt bridge record (wrong magic, bad version, truncated)
  is skipped (one bad record doesn't poison the whole recovery).
- The dispatch path (`cmq_server_publish`) is the same used by
  live bridge traffic, so it honors the existing subject rate
  limits and quota. A replay burst could hit them — that's the
  same DoS surface as the existing replay.

### Reliability

- The replay loop already runs on a worker thread pool
  (`P7_BATCH = 1024` per chunk). Bridge records use the same
  path; no new threading code.
- If `cmq_server_publish` fails (e.g., sublist match OOM), the
  record is dropped — recovery continues to the next record.

## Risk
- Existing client-PUBLISH records should not be affected. The
  magic check (`memcmp(data, "CMQB", 4)`) is robust against
  coincidental matches — `CMQB` is not a valid cmq protocol
  header.
- Replay order: bridge records replay in WAL order. Out-of-order
  delivery is fine for publish (sublist match is idempotent).
