# v0.5.86 — MQTT retain file: same-topic replace contract

## Scope

v0.5.86 adds a defensive test that locks in the
last-write-wins replacement contract for retained-file
recovery.

`cmq_mqtt_store_retained` searches the in-memory retained
array for an existing entry with the same topic and replaces
it. On a server boot, the file is read in order; for each
entry, `cmq_mqtt_store_retained` is called. The contract is:

  - For a given topic, the LAST entry in the file wins.
  - Earlier entries with the same topic are discarded.

This contract is non-trivial: a future regression that
inserts new entries without first checking for an existing
match could leave both entries in memory. The MQTT
semantics expect the most recent publish on a retained
topic to be the one delivered, so file recovery must
honor that.

## What v0.5.86 ships

### Defensive test
(`tests/test_mqtt_retained_file.c`):

- **`mqtt_retained_file.same_topic_second_entry_wins`**:
  writes a retain file with TWO records that share the same
  topic but different payloads. Calls
  `cmq_mqtt_set_retain_path` to load the file. Verifies
  that `cmq_mqtt_fetch_retained` returns the SECOND
  payload and length, not the first.

  The test uses a process-unique file path and a topic
  prefix unique to v0.5.86 (`v0586/...`) so it does not
  collide with state from other tests in the same
  process.

Catches regressions:

- A future change to `cmq_mqtt_store_retained` that
  appends to the in-memory array without checking for an
  existing topic match would let the first entry leak
  into the retained list. The MQTT_MAX_RETAINED cap
  (32) would then deplete faster than expected under
  repeated loads.
- A future change to the file reader that
  short-circuits on the first topic match would prevent
  later records from being recovered.

## Why this matters

Retained files are startup input. A common production
scenario is: broker restarts, retain file has accumulated
thousands of entries over time, many of which are
re-publishes of the same topic as the operator updates
configuration. The replace-by-topic contract is what makes
the file size manageable under this scenario — a
non-replacing reader would let the in-memory store grow
without bound (capped only by MQTT_MAX_RETAINED) and
would deliver stale retained messages to new
subscribers.

## Deferred (unchanged)

- TLS 1.3 mTLS via post-handshake auth. The TLS 1.2 cap
  remains in place; lifting it requires a test framework
  overhaul.
- Per-listener `accept_thread_func` refactor (already on
  remote workstream as v0.5.42).
- Concurrent graceful-shutdown test (framework timing
  issue).
- TLS 1.3 session ticket resumption test (server does not
  issue tickets).
- Retain-file migration from the pre-v0.5.84 two-length
  format to the v0.5.84 single-length format. Existing
  deployments must clear old files before upgrading.
- Full binary-safe retained-file framing. The current text
  format remains newline-delimited and is intended for the
  existing retained-message payload contract.
- ALPN 3+ protocol lists. The current callback code
  handles arbitrary-length lists; a future regression in
  the iteration code could break it. Deferred — a 3+
  list test would consume ~80 LOC of duplicate scaffolding
  for marginal value.
