# CMSGQueue v0.5.1 — Fast-Path Performance Review

Scope: remaining fast-path items that still degrade publish-path latency.
All three findings are on the single-subscriber hot path in
`src/server/cmq_server.c` (`handle_publish` → `snapshot_deliver_targets` →
`deliver_targets_sync` → per-target `worker_push_msg` → `worker_deliver_send_msg`).

## 1. WAL persistence on the publish path — synchronous disk I/O (biggest win)

- **Path:** `handle_publish` → `cmq_filestore_append` (cmq_server.c:2940)
- **Bottleneck:** every PUBLISH with persistence enabled performs, inline,
  `flock(LOCK_EX)` on two fds, `fseeko(SEEK_END)` + `ftello` twice (seq
  refresh and both data/idx), two `fwrite`s, and **two `fflush`es** under a
  global mutex + flock. There is no buffered/async write-ahead stage — the
  publisher thread blocks on the page-cache-to-kernel flush for both the data
  file and the index file on every message. Subscriber fan-out is already
  deferred to worker coroutines (ntgt>16), but the WAL write is not.
- **Predicted cycle delta:** ~800K–1.5M cycles (~250–500 µs at 3 GHz) per
  publish when the fds are cold / cache-missed; ~60–100K cycles even warm.
  This dominates the entire delivery path.
- **Fix sketch:** add a write-ahead ring (SPSC, e.g. 64 KiB chunks) in
  `cmq_filestore.c`; `cmq_filestore_append` becomes a lock-free memcpy into
  the current chunk plus an `eventfd` wakeup. A dedicated WAL thread performs
  the flock/fseeko/fwrite/fflush work in batches, so the publisher returns
  after one buffered memcpy. Add a `sync_interval`/`sync_always` knob; keep
  `cmq_filestore_sync` for explicit durability. Batch the index entry with the
  data write (single flush) instead of two fflushes.

## 2. QG dedup is O(n²) over matched subscribers

- **Path:** `snapshot_deliver_targets` (cmq_server.c:1874–1943), inner loop
  at 1916–1931
- **Bottleneck:** for each queue-group ref, an inner scan walks the rest of
  `result->entries` to collect same-(subject, qgroup, account) members. With
  `N` subscribers across `K` groups this is O(N·K) strcmp work per publish
  (worst case O(N²) when all share one group). `used[]` + `memb[]` are also
  heap-allocated per publish.
- **Predicted cycle delta:** ~40–200K cycles on a 10K-subscriber, 100-group
  subject (each group strcmp ~10–30 cycles × ~1M comparisons), plus the 3
  malloc/calloc/free churn.
- **Fix sketch:** hash groups during the single pass. Walk `result->entries`
  once; for each qgroup ref, hash (subject, qgroup, account) into a small
  open-addressing table mapping to the first member index; round-robin pick
  with `srv->qg_rr_counter` stored per group slot. Dedup becomes amortized
  O(N). Reuse two stack buffers (bounded by a compile-time cap) to kill the
  per-publish allocs.

## 3. Per-target duplicate frame build + copy

- **Path:** `deliver_targets_sync` (cmq_server.c:2123–2180) + `worker_push_msg`
  (cmq_server.c:905–1011)
- **Bottleneck:** one `cmq_build_message_frame` alloc/copy is shared across
  targets (good), but each target then triggers `worker_push_msg`, which does
  a second full `memcpy` of the frame into the worker mailbox buffer — and for
  same-worker targets `deliver_via_worker` calls `client_send_by_id` → a
  **third** copy into `c->write_buf`, plus up to 4 `worker_push_msg` retry
  loops with 50µs `nanosleep` on queue-full. `wakeup_fd_signal` is also called
  once per message, not once per batch.
- **Predicted cycle delta:** ~2–6K cycles per target for the extra copies +
  syscall churn (write() + eventfd + nanosleep on backpressure), ~30K+ per
  queue-full stall.
- **Fix sketch:** for `ntgt ≤ CMQ_CORO_DELIVER_BATCH`, batch same-worker
  targets: build one frame, push a single multi-target mailbox entry (or pass
  a pointer + refcount) so one memcpy reaches all same-worker clients, and
  coalesce `wakeup_fd_signal` to one per drain. Use a per-worker freelist
  (not the 64 KiB global mpool) to recycle mailbox buffers and reuse the
  publisher's frame buffer across targets.

## Tests / Bench harness (Round 3 — added per team review)

**Equivalence tests (behavior-preservation — run under CTest):**
- `perf.wal_append_roundtrip` — for N records, async-ring append → drain →
  `cmq_filestore_read(seq)` returns byte-identical payload + identical seq
  order vs the current synchronous `cmq_filestore_append` baseline.
- `perf.wal_replay_idempotent` — persist → sync → destroy → reopen → replay
  produces identical sublist/delivery state as a sequential-replay reference
  (guards the "no duplicate append during replay" flag).
- `perf.qg_dedup_parity` — `snapshot_deliver_targets` with the O(N²) reference
  vs the hash-based O(N) version must yield the same target set and the same
  round-robin pick sequence for a fixed `qg_rr_counter` seed.
- `perf.batch_same_worker_deliver` — a multi-target publish to same-worker
  subscribers delivers the identical wire bytes per target as the current
  per-message `worker_push_msg` path (guards the single-mailbox-entry change).

**Monotonic perf gate (bench-only — reuse existing harness):**
`examples/benchmark -c 10 -n 10000 -t 1` (the exact workload already
documented in `docs/benchmarks/results.md`). Assert, against a recorded
release-build baseline:
- publish-path p50/p99 latency (currently ~0.029 ms avg on HEAD) does not
  regress beyond measurement noise (±5%);
- end-to-end msg/s does not drop below baseline −5%;
- `stat_messages_dropped` == 0 over the run.

The gate is TDD-able because both the harness and the baseline file already
exist; the bench numbers in the findings above are **estimates** to be
replaced by measured deltas from this gate before merge.

**Durability note (corrected after review):** as of HEAD, `cmq_filestore_sync`
is invoked only from `cmq_server_destroy` (cmq_server.c:7408) — the comment at
cmq_server.c:6620 ("called by the accept loop tick") is stale;
`acceptor_post_tick` (7144) only drains. The current contract is therefore
"per-message fflush to the kernel, no periodic fsync." The async-ring fix
preserves this exact contract (batched fflush, ordered), bounds the ring with
backpressure, and keeps `cmq_filestore_sync` as the explicit durability knob.
True fsync-per-publish durability would be a separate opt-in feature (add
`fsync` to the periodic drain), and is explicitly out of scope for the
fast-path change.
