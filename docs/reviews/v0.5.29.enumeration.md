# v0.5.29 — TLS session ID generation + real resumption test

## Scope
v0.5.28 documented a limitation: OpenSSL 3.5 defaults to ticket-based
resumption for TLS 1.2, leaving the session ID empty. The v0.5.27
cache (keyed by session ID) is therefore exercised by `new_session`
but never by a follow-up `get_cb` — there's no ID to look up.

v0.5.29 closes that gap by:
1. Installing a `SSL_CTX_set_generate_session_id` callback on the
   production server CTX so every fresh session has a non-empty ID.
2. Updating the v0.5.28 placeholder test to verify that the
   resumption path actually triggers our cache's `get_cb` and
   `SSL_session_reused(client_ssl) == 1`.

## Design (performance-first, safety, reliability)

### Session ID generation

```c
static int cmq_tls_gen_session_id(SSL *ssl, unsigned char *id,
                                    unsigned int *id_len);
```

- Allocates a 32-byte random ID via `RAND_bytes`.
- Fills `id` with random bytes.
- Sets `*id_len = 32`.
- Returns 1 on success.

Wired via `SSL_CTX_set_generate_session_id(ctx, cmq_tls_gen_session_id)`
in `tls_build_ssl_ctx`.

### Resumption flow

With ID generation installed:
1. First handshake: server generates session via `gen_session_id`,
   gives it ID = 32 random bytes. `new_session` callback fires;
   our cache stores the session keyed by that ID.
2. Client saves the session. Session has the same ID.
3. Second handshake: client presents the session ID in ClientHello.
4. Server's `get_cb` is called with that ID; looks up in our cache;
   returns the cached session.
5. Handshake completes via resumption; `SSL_session_reused(client_ssl) == 1`.

### Safety

- `RAND_bytes` is OpenSSL's CSPRNG; safe to use for session IDs.
- 32 bytes matches the OpenSSL default session ID length.
- The generation callback is invoked once per session on the
  server side; no thread-safety concerns beyond the cache's own
  mutex (already in place).

### Reliability

- If `RAND_bytes` fails (rare), return 0; OpenSSL will fall back to
  not generating an ID (old behavior).
- The session ID is unique per session (random 32 bytes); collisions
  are statistically impossible.

## Risk
- The `cmq_tls_load` path was already called by v0.5.28. Adding the
  `set_generate_session_id` call there means every `cmq_tls_load`
  installs the callback. Existing tests that do `cmq_tls_load` (the
  v0.5.27/28 tests) might now generate session IDs, which is
  fine — they don't check the ID.
