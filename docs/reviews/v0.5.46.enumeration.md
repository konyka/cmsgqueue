# v0.5.46 — mTLS end-to-end + TLS 1.2 cap for verify_peer

## Scope

v0.5.45 closed the TLS handshake resume bug. v0.5.46 closes the
mutual-TLS (mTLS) end-to-end gap: no test previously drove a
real handshake through `cmq_server_run` with `tls_verify_peer=1`
and verified the runtime effect (server accepts a CA-signed
client cert, rejects an unauthenticated client).

The test exposed a real production bug: mTLS verification was
silently a no-op when the negotiated protocol was TLS 1.3,
because OpenSSL 3.5 / TLS 1.3 changed how the server requests
client certs. v0.5.46 fixes the bug for TLS 1.2 (the dominant
path for mTLS today) and documents the TLS 1.3 follow-up.

## Bug found during exploration

While writing the mTLS test, the second sub-test (unauthenticated
client, must fail) returned `rc=1 verify_result=0` instead of
failing. The client reported a successful handshake even though
it never sent a cert. Diagnostics showed:

- `SSL_CTX_get_verify_mode` returned `0x3` (PEER | FAIL_IF_NO_PEER_CERT).
- `SSL_CTX_get_verify_depth` returned `9`.
- The CA bundle was loaded into the cert store.

Despite all that, OpenSSL accepted the unauthenticated client.

Root cause: TLS 1.3 removed the implicit "CertificateRequest on
verify_peer" behavior. With TLS 1.2, `SSL_VERIFY_FAIL_IF_NO_PEER_CERT`
on the server causes the server to send a CertificateRequest; an
empty Certificate message from the client fails the handshake.
With TLS 1.3, the server must explicitly opt in to the
"client_cert_engine" / post-quantum cert path, otherwise it
never sends a CertificateRequest at all — even with verify mode
set. The server just completed the handshake without asking for
a client cert.

Result: any TLS 1.3 client connected to a server with
`tls_verify_peer=1` was accepted as authenticated, with no cert.

## Fix

Cap the server's SSL_CTX at TLS 1.2 when `verify_peer` is set:

```c
if (cfg->verify_peer) {
    SSL_CTX_set_max_proto_version(cfg->ssl_ctx, TLS1_2_VERSION);
}
```

TLS 1.2 mTLS is the dominant production path; this matches the
existing resumption-cache behavior (v0.5.27–v0.5.29 wired the
cache for TLS 1.2 ID-based resumption). TLS 1.3 mTLS via the
client-cert-engine API is deferred to v0.5.47.

When `verify_peer` is NOT set, the cap is not applied — TLS 1.3
is still the default for normal TLS, preserving performance.

## Test

`tests/test_tls_e2e_handshake.c::mtls_required`:

1. Generate a self-signed CA.
2. Sign a server cert and a client cert with the CA.
3. Configure `cmq_server` with `tls_enabled=1`,
   `tls_verify_peer=1`, `tls_ca=<CA>`.
4. Sub-test A: client with the CA-signed client cert → handshake
   must succeed (`rc == 1`).
5. Sub-test B: client without a cert → handshake must fail
   (`rc != 1`). Server's `SSL_VERIFY_FAIL_IF_NO_PEER_CERT` causes
   the rejection after receiving the ClientHello.

Without the production fix, sub-test B returns `rc == 1` (false
positive). With the fix, `rc == -1` (correct rejection).

## Safety

- The TLS 1.2 cap only applies when `verify_peer=1`. Plain TLS
  (without mTLS) is unaffected.
- TLS 1.2 supports all modern cipher suites used by
  `tls_build_ssl_ctx` (AEAD-only). No cipher list change needed.
- Existing `test_tls_per_listener.c`, `test_tls_e2e_handshake.c`
  tests for TLS 1.2/1.3 negotiation all still pass.

## Performance

- Zero impact on the plaintext path.
- For mTLS, clients must now negotiate TLS 1.2 instead of
  TLS 1.3. TLS 1.3 has slightly lower handshake latency in
  theory, but for mTLS the bottleneck is the cert verification
  (RSA-2048 in test), which dominates either way. Bench:
  ~33K msg/s end-to-end, p99 99.0 µs (unchanged).

## Deferred to v0.5.47+

- TLS 1.3 client-cert path via SSL_CTX_set_client_cert_engine
  or similar API, so the TLS 1.2 cap can be lifted.
- CRL revocation end-to-end test.
- Mutual mTLS through the multi-listener path (each listener
  with its own CA).
